Rust Through disco-snails

Every example is from code you already wrote and shipped.

This is not a general Rust tutorial. It's a tour of the concepts that appear in disco-snails — a Discord thread summarizer you rewrote from TypeScript/Bun into Rust. The goal is to give you mental models for the things you'll encounter most when reading and extending this specific codebase.

Chapters follow the code roughly in the order a new Rust concept appears, not in order of difficulty.

1 Ownership & borrowing

Rust's ownership system has one core rule: every value has exactly one owner at a time. When the owner goes out of scope, the value is freed — no garbage collector required.

In practice, most of the time you're not moving values — you're borrowing them. A &T is a shared (read-only) borrow. The compiler proves at compile time that borrows don't outlive the thing they're borrowing from.

Almost every function in this codebase takes references:

rust · db.rspub async fn get_thread_summary(
    pool: &SqlitePool,
    snowflake: &str,
) -> Result<Option<ThreadSummaryRow>>

&SqlitePool means "borrow the pool, don't take ownership." &str means "borrow a string slice." Neither function owns the pool or the string — they just read from them. The caller still owns both after the call returns.

TypeScript just passes arguments. The runtime keeps everything alive via garbage collection. Rust has no GC — the compiler instead proves statically that borrowed values outlive their borrows. If they don't, it's a compile error, not a crash.

The practical upshot: you'll write & a lot on function parameters. If you see a compile error about "does not live long enough" or "borrow of moved value," that's the ownership checker talking.

2 String vs &str

Rust has two string types, and the distinction matters.

  • &str — a borrowed string slice. A reference to bytes that already exist somewhere. Immutable. Function parameters are almost always &str.
  • String — an owned, heap-allocated, growable string. You produce one when you need to store or build a string.

The pattern appears constantly in this codebase:

rust · discord.rspub fn new(token: impl Into<String>) -> Self {
    Self { http: Client::new(), token: token.into() }
}

impl Into<String> means "accept anything that converts into a String" — both a String and a &str satisfy this. Calling .into() converts it and stores it. This is why you can write:

rustDiscordClient::new("fake")          // &str literal — works
DiscordClient::new(&bot_token)         // &String — works
DiscordClient::new(bot_token.clone())  // String — works

Inside the struct, token: String is an owned value. The DiscordClient owns its token for its entire lifetime — when the client is dropped, the string is freed.

When writing new functions, default to &str for string parameters and String for struct fields. If a function needs to store a string beyond its own scope, it needs ownership — take String or impl Into<String>.

3 Option<T> — no null

Rust has no null, undefined, or surprise None at runtime. A value that might be absent has type Option<T>, which is either Some(value) or None. The compiler forces you to handle both cases before you can use the value.

rust · discord.rspub struct DiscordAuthor {
    pub username: String,
    pub global_name: Option<String>,
}

impl DiscordAuthor {
    pub fn display_name(&self) -> &str {
        self.global_name.as_deref().unwrap_or(&self.username)
    }
}

global_name is Option<String> because Discord users may or may not have a display name. .as_deref() converts Option<String> to Option<&str> (borrowing the inner string), and .unwrap_or() provides the fallback. You cannot accidentally use a None as if it were a string — the type won't allow it.

message.author?.global_name ?? message.author?.username ?? "Unknown user"
The Rust version is more explicit, but the compiler guarantees exhaustive handling. In TypeScript you can forget the ?? fallback and get undefined at runtime.

Option also drives the database return types:

rust · db.rspub async fn get_thread_summary(
    pool: &SqlitePool,
    snowflake: &str,
) -> Result<Option<ThreadSummaryRow>>

This returns Ok(Some(row)) if found, Ok(None) if not found, and Err(...) if the query failed. Three distinct states, all typed, all forced to be handled.

Common Option methods

rustopt.unwrap_or(default)          // value or default
opt.unwrap_or_else(|| expr)      // value or computed default
opt.map(|v| transform(v))        // transform the inner value if Some
opt.as_deref()                   // Option<String> → Option<&str>
opt.is_some() / opt.is_none()   // boolean checks
if let Some(v) = opt { ... }     // destructure and use

4 Result<T> and the ? operator

Rust has no exceptions. Fallible functions return Result<T, E>, which is either Ok(value) or Err(error). You must handle both.

The ? operator is syntactic sugar for: "if this is an Err, return it immediately from the current function; otherwise unwrap the Ok." It makes error propagation cheap to write:

rust · db.rspub async fn open_db(path: &str) -> Result<SqlitePool> {
    let opts = SqliteConnectOptions::from_str(path)?  // early return on err
        .create_if_missing(true);
    let pool = SqlitePool::connect_with(opts).await?; // early return on err
    sqlx::query("CREATE TABLE IF NOT EXISTS ...")
        .execute(&pool).await?;                       // early return on err
    Ok(pool)
}

Each ? is a potential early return. If everything succeeds, Ok(pool) is returned at the end.

The anyhow crate (used throughout) provides a convenient Result type that accepts any error kind, so you don't need to define your own error enum for every module. anyhow::Result<T> is shorthand for Result<T, anyhow::Error>.

.with_context() adds a human-readable message to the error:

rust · main.rsfn env(key: &str) -> Result<String> {
    std::env::var(key).with_context(|| format!("{key} is not set"))
}

When main() propagates this with ?, the error message includes exactly which env var was missing. If you chain multiple .with_context() calls, anyhow builds a full error chain — the Rust equivalent of a stack trace for domain errors.

// TypeScript — exceptions are invisible in the type signature
async function openDb(path: string): Promise<Pool> {
  // could throw, nothing in the type says so
}
In Rust, if a function can fail, Result is in the return type. You can't accidentally ignore an error — the compiler warns if you don't use a Result value.

5 Arc<T> — shared ownership across threads

The borrow checker enforces one owner per value, but sometimes multiple things genuinely need to share ownership — especially across async tasks. That's what Arc<T> (Atomically Reference Counted) is for.

rust · main.rslet discord = Arc::new(DiscordClient::new(&bot_token));

let state = AppState {
    pool: Arc::new(pool.clone()),
    discord: Arc::clone(&discord),  // second pointer, same data
    ...
};

// HTTP server task holds one Arc
tokio::spawn(async move { axum::serve(listener, app).await.unwrap(); });

// Processor loop holds another Arc
loop {
    processor::process_threads(&pool, &discord, ..).await?;
    ...
}

Arc::new(x) puts x on the heap and wraps it in a reference-counted pointer. Arc::clone(&discord) doesn't copy the DiscordClient — it increments the reference count and returns another pointer to the same value. When the last Arc is dropped, the value is freed.

There's also Rc<T> (non-atomic reference counting) for single-threaded use. Since tokio tasks may run on multiple threads, we need Arc. The compiler will tell you if you try to send an Rc across a thread boundary — it simply won't compile.

This is the Rust equivalent of passing an object reference in TypeScript. The difference is the sharing is explicit in the type — you can see from Arc<DiscordClient> that this value is shared — and it's provably thread-safe.

6 #[derive(…)] — free trait implementations

Traits are Rust's version of interfaces. Many common traits can be automatically generated by the compiler using #[derive]:

rust · db.rs#[derive(Debug, Clone, sqlx::FromRow)]
pub struct ThreadSummaryRow {
    pub snowflake: String,
    pub name: String,
    pub ai_summary: String,
    pub last_message_timestamp: i64,
    pub updated_at: i64,
    pub transcript_json: String,
}
  • Debug — enables {:?} formatting for logging and test output
  • Clone — enables .clone() to deep-copy the struct
  • sqlx::FromRow — teaches sqlx how to map a database row into this struct by matching column names to field names

For the transcript message type:

rust · summarizer.rs#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TranscriptMessage {
    pub user: String,
    pub content: String,
}

Serialize and Deserialize (from the serde crate) let you call serde_json::to_string(&msg) and serde_json::from_str::<TranscriptMessage>(s) without writing any serialization code. Field names become JSON keys.

The Discord structs use an attribute to handle a name mismatch:

rust · discord.rs#[derive(Debug, Clone, Deserialize)]
pub struct DiscordChannel {
    pub id: String,
    #[serde(rename = "type")]   // "type" is a keyword in Rust
    pub kind: u8,
    ...
}

#[serde(rename = "type")] tells serde to look for the key "type" in the JSON but store it in the field named kind. Without it, we'd have a naming conflict since type is a reserved keyword.

7 match — exhaustive pattern matching

match is like a switch statement, except the compiler enforces that every possible case is handled. Miss a case and it won't compile.

rust · discord.rsfn url_encode(s: &str) -> String {
    s.bytes().map(|b| match b {
        b'A'..=b'Z' | b'a'..=b'z' | b'0'..=b'9'
        | b'-' | b'_' | b'.' | b'~' => (b as char).to_string(),
        _ => format!("%{b:02X}"),
    }).collect()
}

b'A'..=b'Z' is a range pattern. | joins multiple patterns in one arm. _ is the catch-all. Every possible u8 value is covered.

Where match really shines is on enums. The DiscordUri enum has three variants, and every place it's used must handle all three:

rust · server.rsenum DiscordUri {
    Message { channel_id: String, message_id: String },
    Channel { channel_id: String },
    Thread  { channel_id: String },
}

match parsed {
    DiscordUri::Message { channel_id, message_id } => { ... }
    DiscordUri::Channel { channel_id }             => { ... }
    DiscordUri::Thread  { channel_id }             => { ... }
}

If you added a fourth variant and forgot to handle it in any match, the compiler would refuse to build. TypeScript's switch on a discriminated union gives you a lint warning at best.

if let is a shorthand for matching one variant and ignoring the rest:

rustif let Some(existing) = get_thread_summary(pool, &thread.id).await? {
    if existing.last_message_timestamp == last_ts {
        skipped += 1;
        continue;
    }
}

8 async / await

Rust's async/await looks like JavaScript's, but there's one key difference: Rust async functions are lazy. Calling an async function does nothing until you .await it. There's no implicit scheduling.

rust · processor.rspub async fn process_threads(
    pool: &SqlitePool,
    discord: &DiscordClient,
    ...
) -> Result<()> {
    let thread_batches = discord
        .fetch_thread_messages(forum_channel_id, lookback)
        .await?;  // drive future to completion, propagate error
    ...
}

The .await? combines two things: .await drives the future to completion, and ? propagates any error. It's the pattern for every fallible async call.

The tokio runtime drives all futures. #[tokio::main] in main.rs is a macro that sets up the runtime:

rust · main.rs#[tokio::main]
async fn main() -> Result<()> { ... }

Without it, there'd be nothing to execute the futures — calling an async function gives you a Future object, not a running task.

tokio::spawn runs something concurrently without awaiting it:

rust · main.rstokio::spawn(async move {
    axum::serve(listener, app).await.unwrap();
});

This launches the HTTP server as a background task and immediately continues. async move means the closure captures its variables by ownership — required because spawned tasks may outlive the current scope.

In JavaScript, Promise execution starts immediately on creation. In Rust, Future execution starts only when polled (i.e., awaited). This makes Rust async more predictable — nothing runs until you tell it to.

9 Iterators & closures

Rust's iterator methods (map, filter, collect, chain, flatten, etc.) compile down to tight loops with no overhead. They're used heavily throughout this codebase.

rust · processor.rslet transcript: Vec<TranscriptMessage> = messages.iter().map(|m| TranscriptMessage {
    user: m.author.as_ref()
        .map(|a| a.display_name().to_string())
        .unwrap_or_else(|| "Unknown".to_string()),
    content: m.content.clone(),
}).collect();

Breaking it down:

  • .iter() — borrows each element; gives &DiscordMessage
  • .map(|m| ...) — transforms each element; m is the closure argument
  • .collect() — drives the iterator to completion and gathers results into a Vec. The type annotation on the left tells Rust what to collect into.

Chaining iterators — here, combining active and archived threads:

rust · discord.rsactive_here.into_iter().chain(archived.threads).collect()

.into_iter() consumes the Vec (takes ownership). .chain() appends another iterator. .collect() materializes it into a new Vec.

Flattening nested Vecs:

rust · discord.rsr.messages
    .unwrap_or_default()  // Option<Vec<Vec<T>>> → Vec<Vec<T>>
    .into_iter()          // Iterator<Item=Vec<T>>
    .flatten()            // Iterator<Item=T>
    .collect()            // Vec<T>

Closures use |args| body syntax. || expr is a zero-argument closure (equivalent to () => expr in TypeScript). The move keyword makes a closure capture variables by ownership rather than by reference.

10 Lifetimes

Most of the time, Rust infers lifetimes automatically through a set of rules called lifetime elision. You rarely write them. But one lifetime annotation appears in this codebase and is worth understanding:

rust · discord.rsasync fn get<T: for<'de> Deserialize<'de>>(&self, path: &str) -> Result<T>

for<'de> Deserialize<'de> is a higher-ranked trait bound. It means: "T must implement Deserialize for any possible lifetime 'de."

Why is this needed? Serde's Deserialize trait is parameterized by the lifetime of the input data — Deserialize<'de> means "deserialized from data that lives at least as long as 'de." When you deserialize from a temporary buffer (as reqwest's .json().await? does), you need to guarantee that T doesn't hold references into that buffer that outlive it.

for<'de> says "this must work for any lifetime, including very short ones." In practice this means T must be fully owned — no borrowed references to the input. Any type with #[derive(Deserialize)] and only owned fields (like String, not &str) satisfies this automatically.

You'll see for<'de> Deserialize<'de> whenever you write a generic function that deserializes from a temporary source. It's a fixed phrase — just use it as-is, the same way you'd use async fn.

11 Modules

Each file in src/ is a module. mod db; in main.rs tells the compiler to find and compile src/db.rs. Items inside a module are private by default; pub makes them visible to callers.

rust · main.rsmod db;
mod discord;
mod processor;
mod server;
mod summarizer;

Within a module, reference other modules with crate:::

rust · processor.rsuse crate::db::{get_thread_summary, upsert_thread_summary};
use crate::discord::DiscordClient;
use crate::summarizer::{TranscriptMessage, summarize_thread};

use brings names into scope so you don't need the full path every time. crate:: is an absolute path starting from the crate root.

Test modules are conventionally inline, compiled only during cargo test:

rust · db.rs#[cfg(test)]
mod tests {
    use super::*;  // imports everything from the parent module

    #[tokio::test]
    async fn upsert_and_get_roundtrip() {
        ...
    }
}

use super::* gives tests access to private internals of the module they're testing. #[cfg(test)] gates the module — it doesn't exist in the production binary.

12 A request end-to-end

To see how all these pieces connect, trace a single MCP read_thread_summary call through the stack:

1. axum receives the request

handle_mcp is called with State(state) — axum extracts the AppState from the router using the Clone derive on AppState (which clone-bumps the Arc counts, not the underlying data).

2. Body is deserialized

serde_json::from_value::<JsonRpcRequest>(req_val) — the #[derive(Deserialize)] on JsonRpcRequest made this zero-boilerplate. Field names match the JSON keys.

3. match routes to the right tool

rust · server.rsmatch req.method.as_deref() {
    Some("tools/call") => {
        match name {
            Some("read_thread_summary") => { ... }
        }
    }
}

4. thread_id extracted as Option

rustlet thread_id = match get_str(args, "thread_id") {
    Some(t) => t.to_string(),
    None => return Some(rpc_error(id, -32602, "...")),
};

5. Rows searched by iterator

rustlet row = rows.iter().find(|r| r.snowflake == lookup)
    .or_else(|| rows.iter().find(|r| r.name == thread_id));

Borrows each row with &, no copying. Returns Option<&ThreadSummaryRow>.

6. Response built from owned String

rustSome(rpc_result(id, mcp_text(render_thread_summary_markdown(r))))

render_thread_summary_markdown borrows all the row's fields (&row.name, etc.) and builds a new String. mcp_text wraps it in a serde_json::Value using the json! macro.

7. Response serialized and sent

serde_json::to_string(&responses[0]) — Value implements Serialize, so this is a single function call. Wrapped in an axum Response with the appropriate content-type header.

The entire path is synchronous-looking but fully async. Every .await is a point where the tokio executor can run other tasks — other HTTP requests, the background processor timer — while waiting on I/O.

13 Cargo & the ecosystem

Cargo is Rust's build tool, package manager, test runner, doc generator, and benchmark harness — all one command. There's no npm/webpack split; the whole build is a single mental model.

Cargo.toml

The manifest lives at the repo root. Here's the disco-snails one, annotated:

toml · Cargo.toml[package]
name = "disco-snails"
version = "0.1.0"
edition = "2021"     # language edition; 2021 is the current stable one

[[bin]]              # double brackets = array; one entry per binary
name = "disco-snails"
path = "src/main.rs"

[dependencies]
tokio = { version = "1", features = ["full"] }
axum  = { version = "0.8", features = ["json"] }
sqlx  = { version = "0.8", features = ["sqlite", "runtime-tokio"] }

[dev-dependencies]  # only compiled for `cargo test`
axum-test = "20"
tempfile  = "3"

Features are opt-in capability flags inside a crate. tokio = { features = ["full"] } enables all of tokio (timers, I/O, the macros, etc.). reqwest = { default-features = false, features = ["rustls-tls"] } strips the default OpenSSL dep and uses the pure-Rust TLS implementation instead — important for musl/Docker builds.

The key commands

shell# build + run (debug, incremental, fast)
cargo run

# optimized release binary (slow first compile, fast binary)
cargo build --release

# run all tests
cargo test

# run only the db module's tests
cargo test db::

# lint with suggestions
cargo clippy

# format in place
cargo fmt

# open local docs for all deps at your exact versions
cargo doc --open

# audit your dependency tree for known CVEs
cargo audit

# show what's taking so long to compile
cargo build --timings

Cargo.lock

Like package-lock.json but for the whole build. Commit it for binaries (you want reproducible builds), omit it for libraries (you want dependents to pick their own versions). disco-snails is a binary, so it's committed.

crates.io

The central registry. Every cargo add or Cargo.toml dependency resolves through it by default. Docs auto-publish to docs.rs on every crate version — so docs.rs/axum shows fully rendered API docs for the exact version you're using, with source links.

Workspaces

A workspace is a multi-crate repo under one Cargo.toml. All crates share a single Cargo.lock and a single target/ directory. disco-snails is a single-crate repo (no workspace), which is the right call at this size. You'd add a workspace if you split out e.g. a shared disco-snails-types crate.

npm has package.json + package-lock.json + node_modules + a separate bundler + a separate type-checker + a separate linter. Cargo is all of those in one tool with one config file. The tradeoff: compile times are long on a cold cache.
